# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Команды

```bash
npm run dev     # npx serve на http://localhost:5173
```

Сборки, линтера и тестов в проекте нет. Единственный способ проверить изменение — поднять сервер и прокликать раздел в браузере; после правок делай это сам, не дожидаясь просьбы. Открывать `index.html` через `file://` бесполезно: ES-модули не грузятся из-за CORS.

## Жёсткие ограничения

**Никаких фреймворков, сборщиков и зависимостей.** Владелец изучает фронтенд по книгам Jon Duckett и должен понимать каждую строку. Предложение «возьмём React/Vite/TypeScript» ломает цель проекта. Код держим читаемым: нативные ES-модули, понятные имена, без плотных однострочников.

Комментарии в коде — на русском, объясняют *почему*, а не *что*. Придерживайся этого стиля.

## Архитектура

Всё приложение — три слоя, поток данных строго в одну сторону:

```
modules/ (UI)  →  services/ (логика)  →  data/storageAdapter.js (контракт)  →  localStorageAdapter.js
```

UI никогда не трогает `localStorage` напрямую (исключение — мелкие UI-настройки вроде последнего выбранного цвета). При переходе на Supabase меняется ровно одна строка — `ACTIVE_ADAPTER` в `storageAdapter.js`; JSDoc-typedef там же описывает контракт, который обязан реализовать новый адаптер.

**Роутер** (`app.js`) — hash-based (`#/notes`, `#/calendar`, пусто = главная). Каждый переход полностью очищает `#app-view` и перерисовывает раздел заново. Состояние живёт в модульных переменных вьюх, не в DOM.

**Notes** (`modules/notes/notesView.js`) — единственный раздел заметок, раньше разделённый на Задачи и Документы, теперь слитый в один. Он вызывает `renderPanelSection(container, config)` из `modules/shared/panelSection.js` с `section: "notes"`. Тулбар сворачиваемый: `config.toolbarButtons` — полный набор, `config.basicToolbarButtons` — сокращённый (бывший набор Задач), кнопка "+/−" в тулбаре переключает между ними, состояние живёт в `localStorage` (`app:toolbarExpanded`). В хранилище `matchesSection()` в `localStorageAdapter.js` считает `"tasks"`, `"documents"` и `"notes"` алиасами — старые записи с легаси-метками `tasks`/`documents` остаются доступны под текущим `"notes"` без миграции.

**Ключи localStorage:** `app:folders`, `app:items`, `app:diaryEntries`, `app:calendarEntries`, `app:calendarTags`. Настройки (`app:lang`, обводка, последние цвета) живут под своими ключами и намеренно переживают «очистить данные».

## Сквозные соглашения

**Esc и слои.** `utils/escapeLayers.js` — единая точка. Всё, что визуально лежит поверх страницы (контекстное меню, модалка, поповер, панель настроек), обязано зарегистрироваться через `pushLayer(close)` и снять регистрацию при закрытии любым другим способом. Esc закрывает верхний слой, по одному за нажатие; когда слоёв нет — уводит из поля ввода, затем на шаг назад по навигации (`setViewEscape`, роутер сбрасывает его перед каждым рендером). Добавляешь новый оверлей — подключай к этой системе, не вешай собственный `keydown`.

**Закрытие модалок и меню.** Закрывать можно только по клику, *начавшемуся* снаружи (слушаем `mousedown`, не `click`), и по Esc. Иначе зажатие кнопки внутри окна с отпусканием снаружи схлопывает окно — этот баг уже чинили, не верни его.

**i18n.** Ни одной строки UI в разметке напрямую — только через `t("ключ")`. Новый ключ добавляется сразу в оба языка в `i18n/translations.js`. Дефолт — английский, русский переключается в настройках; смена языка перерисовывает текущий раздел.

**Экранирование.** Вьюхи строятся через шаблонные строки и `innerHTML`, поэтому любые пользовательские данные прогоняй через `escapeHtml()` / `escapeAttr()` из `utils/dom.js`.

**Редактор** (`modules/shared/richTextEditor.js`) — на `contenteditable`. Кнопка `"italic"` определена, но намеренно убрана из тулбаров: чтобы вернуть, достаточно снова вписать её в список в `notesView.js`. У цветовых кнопок особая логика: ЛКМ красит последним выбранным цветом, ПКМ открывает палитру. `pageMode` (`"flow"` | `"paged"`) хранится в самой заметке.

## Рабочий процесс

Большие ТЗ приходят структурированными, с блоком «ПОРЯДОК РАБОТЫ» в конце — иди строго по пунктам, по одному за раз, а не всё сразу. Для крупных задач сначала покажи план и дождись одобрения.

Коммит — только когда работа доведена до конца И владелец дал явное разрешение (оба условия сразу); формулировка «после каждого шага — commit» в самом ТЗ разрешением не считается, это может быть старый шаблон. Спросить один раз в конце работы можно, коммитить по ходу без спроса — нет. Сообщение коммита — описательное (`feat: rename folders and notes in place`, не `fix`). Push — тем более только по прямой просьбе.
